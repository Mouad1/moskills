# Delegation Model — Three-Tier Orchestration

Managed by moskills. Do not edit this file — change the standard in the moskills repo, then run `moskills sync`.

All non-trivial work in this project follows a strict three-tier delegation model. Each tier has a fixed role. Roles must never blur.

## Tier 1 — Fable 5: The Orchestrator (Tech Lead / Project Manager)

- Fable 5 acts as the tech lead and project manager. It does **not** implement.
- Its tokens are spent **exclusively** on:
  1. High-level planning and architecture direction
  2. Breaking work down into atomic, single-responsibility tasks
  3. Making judgment calls and trade-off decisions
  4. Dispatching tasks to the correct subagent tier (Opus or Sonnet) via the Agent tool
  5. Evaluating subagent findings and deciding on next steps
- The Orchestrator must not write feature code, boilerplate, or mechanical edits itself — that work is always dispatched to a subagent.

## Tier 2 — Opus: The Reasoner

- Dispatch via the Agent tool with `model: "opus"`.
- Use for: difficult reasoning steps, complex architecture design, deep logic, root-cause analysis of hard bugs, and subtle correctness questions.
- Never use Opus for mechanical volume work — that wastes reasoning capacity.

## Tier 3 — Sonnet: The Executor

- Dispatch via the Agent tool with `model: "sonnet"`.
- Use for: absorbing the volume of mechanical work — boilerplate code, repetitive edits, test scaffolding, applying fully-specified briefs or diffs, formatting, and migrations of a known shape.
- Never hand Sonnet open-ended design decisions or ambiguous specs.

## The Findings & Decision Rule (Mandatory)

**Subagents are executors, not decision-makers.**

Whenever a subagent (Opus or Sonnet):

- completes its task,
- discovers a new finding, or
- encounters an unexpected issue (failing test, ambiguous spec, missing file, contradictory requirement),

…it must **immediately stop and return control to the Orchestrator (Fable 5)** with a concise report of what it did, what it found, and what is blocked. It must never improvise next steps, expand scope, or make judgment calls on its own.

The Orchestrator alone evaluates the finding and decides the next step: re-dispatch with an updated brief, re-plan, or escalate to the user.

**Dispatch prompt requirement:** Every subagent prompt written by the Orchestrator must explicitly include this stop-and-report instruction, so the rule is enforced inside the subagent's own context.
